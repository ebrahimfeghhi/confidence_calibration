# The validation set

**THE single file for how the validation set was chosen and what it is.** Everything that feeds the
selection is here; `cluster_composition.md` is a generated data appendix (one row per cluster in the
whole pool) and `training_data_overview.md` describes the pool the split was drawn from.

Status: **LAUNCHED 2026-10-12 17:43 PT.** 40 clusters, one representative each, 100 seeds, folding on
GPUs 0/1/3 as dataset `sabdab_val2`. Generated by `scripts/propose_val_split.py`, which is the
authority on the procedure. Revised after two review rounds; see *Corrections* for what changed.

## Where it came from

The pool is the SAbDab2 antibody-antigen set restricted to the 533 clusters that survived the
homology audit against FoldBench and PXM-2025: 3,617 structures, 5,983 instances, of which 1,757
structures are post-cutoff. Phase B originally drew 50 validation clusters from those 533, stratified
into 5 bins by median deposition date, 20,000 random draws under seed 20261010, rejecting any draw
where one cluster exceeded 15% of the target.

Restricting validation to post-cutoff structures collapsed that to 21 live clusters: 26 of the 50
hold no post-cutoff structure at all and 3 hold one that was never folded. That is what prompted the
redesign. The 21-cluster fold's results (10 decoy / 30 acceptable / 14 no-acceptable at 30 seeds over
54 interfaces) remain reproducible: its `pool.csv`, poses and scores are untouched under `val_fold`,
and `sabdab_val` still points at them.

### Composition of the pool, by era

| group | clusters | complexes | post-cutoff complexes |
|---|---|---|---|
| all new (no pre-cutoff structure) | 141 | 279 | 279 |
| mixed (both eras) | 107 | 2,601 | 1,486 |
| all old (no post-cutoff structure) | 285 | 747 | 0 |
| **total** | 533 | 3,627 | 1,765 |

84% of post-cutoff data sits in mixed clusters, and the 141 all-new clusters average 2 complexes
each. 71% of all clusters with any post-cutoff structure have exactly one -- an `ab_ag_cluster` is
one antibody lineage against one antigen, and most such systems are deposited once. That is why 27
of the 40 selected clusters have no second representative available (21 genuinely have one structure;
6 have more but the extras fail the polypeptide-antigen or 150-token filters).

## Why redesign

Restricting validation to post-cutoff structures left 21 of the original 50 clusters live: 26 hold
no post-cutoff structure at all and 3 hold one that was never folded. 21 clusters is a thin holdout
when one interface is ~2% of the signal, and phase B's draw controlled for deposition date and
nothing else -- not complex size, not how much training data a cluster withholds, not redundancy.

## Rules, applied identically to retained and sampled clusters

| rule | threshold | why |
|---|---|---|
| **R1** size | representative <= 1000 tokens | the cache grows as N^2. `z_trunk` is `[N, N, 256]` in bf16 -- **measured**, 96% of the npz, and npz gives no compression (a 250-token file is 32 MB uncompressed and 32 MB on disk). One 1,200-token structure costs as much as six at 500 |
| **R2** withholding | cluster holds <= 5 post-cutoff structures | holding a cluster out removes every structure in it from training; the post-cutoff ones are the costly half |
| **R3** composition | 24 all-new + 16 mixed, asserted | *all new* = nothing in the cluster predates 2021-09-30, so no relative can have been in Protenix's pool. *mixed* = a post-cutoff structure of a system Protenix has older structures of. Reported separately. The generator now FAILS if it cannot fill both quotas rather than writing a short set |
| **R4** redundancy | **flagged, not enforced** | see Corrections |

**R2 defines the population the result describes.** Capping withheld post-cutoff structures at 5
deliberately builds a validation set of *small* clusters -- systems with few post-cutoff
structures. That serves the goal of preserving training data, but any performance claim must be
stated for that population, not for antibody-antigen complexes in general.

## Eligibility and pricing follow the production code

- **Eligible rows**: only rows whose `agtypes` includes `PROTEIN` or `PEPTIDE`, matching
  `phase_a_define_train_set.py:118,262`. Without this filter a hapten-only pairing can be picked as
  a cluster's representative.
- **Token count**: `len(Hseq) + len(Lseq) +` the `agEXPECTEDseqs` entries whose `agtypes` is
  polypeptide, which is what `phase_g_build_val_jobs.py:154-165` actually folds. `agresolvedseqs`
  is the resolved subsequence and shorter, so using it under-prices the fold -- and the error is
  squared in cache bytes.
- **The instance is carried**, not just the cluster and pdb, so the application step can fold the
  exact pairing that was reviewed.

**22 of 40 representatives are still priced by the formula, not by a built job json.**
Those must be re-priced from real job jsons before the split is frozen. Repricing can change R1
eligibility, which token stratum a cluster falls in, and therefore which clusters are sampled -- so
the membership below is provisional for those rows.

not exempt ones. Three failed:

## Retained-plus-sampled versus a fully redrawn set

The control for reuse: retaining audited clusters saves refolding them, but could carry phase B's
selection bias forward. A fully redrawn 40 under the *same* rules is the comparison. Reproduce with
`propose_val_split.py --compare`.

| axis | retain 18 + sample 22 | fully redrawn 40 |
|---|---|---|
| clusters | 40 | 40 |
| all-new / mixed | 24 / 16 | 24 / 16 |
| complex size min/median/max (tokens) | 231 / 482 / 799 | 239 / 524 / 837 |
| cluster population, median post-cutoff structures | 1 | 1 |
| post-cutoff structures withheld | 66 | 72 |
| pre-cutoff structures withheld | **210** | **132** |
| cache at 100 seeds | 550 GiB | 573 GiB |
| already folded | 18 | 3 |

They agree on composition, cluster population, complex size and cache. Two differences matter:

- **Reuse withholds 78 more pre-cutoff structures** (210 vs 132). Phase B stratified on deposition
  date, so the retained clusters skew older and carry more pre-cutoff relatives -- cluster 13 alone
  holds 41. This is the one axis where reuse is worse. It is the cheaper half of the training data,
  since those are the structures Protenix already fits, but it is a real cost and not zero.
- **Reuse starts with 18 of 40 already folded** against 3, which is the compute saving that motivates
  it at all.

So reuse is defensible but not free, and the trade is: 78 pre-cutoff training structures for 15
clusters that do not need refolding.

## Freeze checklist (all items done before launch)

1. **Re-price the 22 formula-priced representatives** from real job jsons, then re-run the
   selection. Eligibility and strata can change.
2. **Build jobs from the explicit instances**, not from cluster ids. Phase G today takes a cluster
   list and picks its own representative across both eras, so handing it this file would not
   reproduce these 40 jobs. The application step must consume the `instance` column and then assert
   that the resulting `val_jobs/manifest.csv` matches this proposal row for row.
3. **Check MSA coverage per chain** for the sampled clusters; it is not guaranteed outside the
   already-folded set.
4. **Fix the seed depth** (100, or a uniform 80) and freeze it.
5. **Write the split through phase B's guard** so the exclusion check runs, and move every
   non-selected cluster back to training -- whole clusters only. A selected cluster's pre-cutoff
   structures must stay out of training: training on a 2015 structure of a system validated on its
   2023 structure is cluster-level leakage.
6. **Record the file's hash** before any model comparison.

## Corrections (2026-10-12, after review)

| what was wrong | effect |
|---|---|
| no polypeptide-antigen filter, so every row in a cluster was a candidate | a hapten pairing could be selected as a representative; eligible pool was 124/80, correctly 130/60 |
| tokens summed `agresolvedseqs` instead of the `agexpectedseqs` phase G folds | sizes were under-priced, and the error is squared in cache bytes |
| R4 dropped one of any pair sharing a deposition date and token count | it removed cluster 1882, whose `8t05` differs from 1833's `8t04` in heavy chain, light chain AND antigen sequence -- distinct systems. R4 now only flags, and a drop requires identical folded input |
| the instance was not carried | the application step could not fold the exact reviewed pairing |
| a short set was written silently when a stratum ran dry | the generator now fails unless `--allow-short` |
| sizes labelled GB when computed in GiB | 550 GiB is 590 GB decimal |

The `z_trunk` channel count was questioned and is settled by measurement, not assumption: a real
dump is `(250, 250, 256)` uint16, 31 MB of a 32 MB file, so pair channels are **256** and bytes per
seed are `N^2 x 512`. An estimate at 128 channels is half the truth.

### What was done

**1. Stop the fold in flight, by PID.** Kill the `vf_run100` orchestrator, then check for orphaned
`vf_val_*` sessions and kill those by PID too -- the trap has been observed NOT to fire -- then
`reconcile_stale_claims.py val_fold --dataset sabdab_val` to release claims held mid-fold.

**2. Migrate the 18 structures the new split retains**, `val_fold` -> `val2_fold`: their
`poses/<pdb>/` and `trunks/<pdb>/` directories, and their rows from `results.csv`. Without this
`folder.py` reads an empty `val2_fold/results.csv` and refolds all 40, discarding 132 GiB of cache
and ~9 GPU-h. 7 of the 18 are already at 100/100 seeds; the other 11 are at 20/100 and resume.

| | structures | trunks | poses |
|---|---|---|---|
| migrate | 18 | 132 GiB | 1.7 GiB |

**3. Delete what the new split drops**: 10 structures, **119 GiB of trunks**. Four are clusters the
audit rejected (`9dzh` and `9dzf` from cluster 1867, `9p4f` from 2611, `9hvw` from 764) and six are

**4. Verify before any GPU.** `phase_i_inputs.py --jobs val2_jobs` again after the moves, then the
smoke gate -- one unit end to end, asserting a pose, a per-fold npz with every confidence-head
tensor, a numeric DockQ, a numeric ipTM and a summary-confidence json.

**5. Launch.**

4,000 units (40 x 100). The migration brings **920** finished units -- 7 structures at 100 seeds and
11 at 20 -- so **3,080 remain to fold**: 28 GPU-h, about 9.3 h on three cards. (An earlier draft said
"1,780 done, 2,220 to fold". That was prose arithmetic contradicting the estimator that produced the
28 GPU-h, which was computed from 3,080 units. 920/3,080 is the measured split, recomputed over the
retained structures only and the 400000-400099 range.)

The smoke step picks an unfolded unit by `phases/pick_unfolded_unit.py` and asserts against that unit
by name. Its default -- the first active structure at SEED0 -- is a completed retained unit after the
migration, which `folder.py` skips; the assertions used to count artifacts anywhere under the fold
directory and would have passed on migrated data. They are now scoped to the chosen unit: new cif
count strictly greater than before, a `results.csv` row for that pdb and seed, a summary-confidence
json, and the npz validator opens `<pdb>/free_<seed>.npz` rather than whichever sorts first. The
helper exits non-zero if every expected unit is already folded, so `SMOKE_OK` cannot be written
without a fold having happened.

### Known loose ends

- **22 of 40 structures have never been folded**, so their fold time is modelled, not measured.
- **The `9dzf` second-structure rule is not enforced in code.** The split is one structure per
  cluster by construction; nothing stops a later `--reps 2` run from reintroducing a second.
- **Phase H on a subset relaxes a shared chain directory's cutoff.** Running it on `val2_jobs`
  rewrote `c1332_7cj2_ag0_787a8b` from pre-cutoff `7cj2`'s strict date to the 2021-09-30 cap, because
  `val2` contains only post-cutoff `8df1`. Harmless here -- `8df1`'s 100 seeds all completed at
  17:22, five minutes before the rewrite, and `7cj2` is in `skipped.csv` and never folded -- but any
  future refold of a pre-cutoff structure must re-run phase H first, and `phase_i_inputs.py` is the
  gate that catches it.

### How to launch it

Append the 13 instances to a manifest and build them by **explicit instance**, never `--reps 2` --
phase G's own second pick is the cluster median by token count, which is both unreviewed and the
expensive end.

    # 1. the manifest already exists: results/val_split_second_reps.csv, written by
    #    scripts/pick_second_reps.py -- 40 first + 13 second = 53 instances, rule in code
    # 2. phase G, explicit instances, into the SAME val2 dirs so the fold is one set
    python3 phases/phase_g_build_val_jobs.py --instances results/val_split_second_reps.csv \
        --val-clusters results/val_split_proposal_clusters.csv \
        --msa-root  $PWD/msa_work/mmcif_msa --excluded results/excluded_homolog_clusters.csv \
        --seq-index $PWD/msa_work/pdb_seqs/seq_to_pdb_index.json \
        --out-dir $PWD/val2_jobs --fold-dir $PWD/val2_fold --refs-dir $PWD/val2_refs
    # 3. phase H on val2_jobs, then phase_i_inputs.py, then smoke, then run

Two gates that must not be skipped. Phase G's `--instances` rebuilds `val2_fold/pool.csv` for the
**whole** job set, so re-run it with all 53 instances, not just the 13, or the 40 already folded lose
their interface definitions. And re-run `phase_i_inputs.py`: adding structures changes the cutoff the
job set requires, and a template directory filtered for the old set can be too permissive for the new
one.

### Reporting convention, fixed before training

Average the representatives **within** each cluster first, then weight the 40 clusters equally. A
cluster with two structures must not count twice. All-new and mixed arms stay reported separately.
