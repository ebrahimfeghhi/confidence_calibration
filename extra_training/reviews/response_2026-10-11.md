## The find that mattered most

`classify()` kept **one hmmscan hit per chain**, ranked by **column 7 — the full-sequence E-value**.
That value is a property of the (query, target) pair, so every domain of a chain carries it
identically: 8r4u_B's two halves both read 5.0e-64 against `human_L`. Ranking on it cannot distinguish
a VH from a VL even in principle, and `human_H` hit that same chain at 1.9e-57.

Single-chain constructs carry two variable domains (8r4u_B is 236 residues, envelopes 1-127 and
126-236). Four of the 39 unlisted complexes — 8r4u, 9gry, 9gs3, 9i20 — consist only of such chains, so
they contributed **no CDR-H3 query at all**, and Filter 3 reported 0 for them whether or not a leak
existed.

Now one entry per domain, ranked by the per-domain i-Evalue, with overlapping envelopes merged:

| | before | after |
|---|---|---|
| heavy domains | 60 | **67** |
| complexes contributing a CDR-H3 | 35 | **39 of 39** |
| Filter 3 hits | 0 | 0 |

The reviewer who predicted this described the mechanism exactly — "an scFv whose best hmmscan hit
lands on an `_L` model is classified L, drops out of heavy, and its CDR-H3 is never queried."

## Not adopted: banding the held-out structure count as the default

The diagnosis is right — argmin over 20,000 draws does select an extreme draw, and I can quantify it.
Of 20,000 draws, 11,296 pass the dominant-cluster rule; their held-out share runs 2.4% to 10.1%,
median 4.5%. `--frac 0.10` therefore selects the single **largest-holdout draw of the 11,296**.

The stated rationale is what I could not confirm: that the held-out structure count "only affects how
much training data you give up, not the validation set itself." It affects the validation set
directly.

| cluster size | clusters | can supply 2 representatives |
|---|---|---|
| 1 structure | 305 | **0%** |
| 2 | 96 | 100% |
| 3–5 | 96 | 100% |
| 6+ | 60 | 100% |

55% of clusters are singletons, so the held-out structure count is close to a proxy for how many
clusters can supply a second representative. Switching cost **79 → 72 folded structures**.

Narrowing the band does not help: [8%, 12%] leaves 25 draws of 20,000 and [9%, 13%] leaves 2 — argmin
again, with none of the bias removed. Held-out share is also a noisy proxy for folded count: [8%, 12%]
holds out *more* structures (236) yet folds *fewer* (71) than [5%, 12%] (161 → 72). If this is
revisited, the quantity to constrain is folded representatives, not structures.

And the bias has no established direction. Large clusters here are **newer**:

| cluster size | median deposition | % of structures before Protenix's 2021-09-30 cutoff |
|---|---|---|
| 1 | 2019-10-09 | 64% |
| 2 | 2018-09-17 | 68% |
| 3–5 | 2019-12-23 | 65% |
| 6+ | **2021-07-30** | **39%** |

So they are *less* likely to sit inside the model's training data — if anything harder, not easier.
Rank correlation between cluster size and date is 0.04. Post-cutoff coverage is identical either way,
17 of 50 clusters, which the date binning guarantees.

`--select target` therefore remains the default and `val_clusters.csv` is unchanged: it is an extreme
draw on cluster size, in a direction not shown to flatter the result, and it buys 7 more folded
structures. `--select band` is implemented and documented so the alternative is available once
per-cluster DockQ exists to measure the two against each other.

## Corrected framing

**The 0-shared check is a smoke test, not a test of the filters.** It was described as "testing all
three filters at once," and I initially wrote that into the README as established. Identity 1.0 is the
*easiest* case any filter faces — filter 2 sits at 0.40 for proteins, filter 3 at 0.95 — and filter 1
usually removes such a cluster by id before sequence comparison is reached. Passing says the exclusion
catches the trivial case; it says nothing about whether the thresholds are calibrated. Worth having at
two lines; the code and README now say what it does and does not cover.

**Filter 3's "0 clusters removed" is not independent confirmation.** It is honestly earned now — 39 of
39 complexes queried, every pair compared — but it was always close to expected. SAbDab2's
`ab_ag_cluster` is a connected component over shared antibody *or* antigen cluster, so any cluster
sharing an antibody with one of the 188 listed complexes is already removed by filter 1. Filter 3 can
only ever speak to the 39 unlisted ones.

**`train_minus_val()` is insurance, not a guarantee.** It is the only enforcement of the split, and
nothing calls it yet because the training stage does not exist. A function nobody is obliged to call
does not prevent the failure it was written for. The stronger form is for phase B to emit a
`train_clusters.csv` that the training stage reads as its only input, so using the full 557 requires
deliberately going around the pipeline. Worth doing when that stage is written.
