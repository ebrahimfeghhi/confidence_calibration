# Code review — `extra_training`, 2026-10-13

Review of the 7,394 lines under `extra_training/phases/` and `extra_training/shell_scripts/`, prompted by
a confirmed train/validation leak. Findings are ordered by severity. Each one names the file and
line, what breaks, and whether it is fixed.

**Coverage.** This was not a line-by-line read of all 32 files. It was: (a) a cross-file trace of
which artefact each script reads for the train/validation split, (b) a scan for fail-open patterns —
broad `except`, silent fallbacks, and failure values that mean "no problem found" in a leakage check,
(c) a close read of `phase_a_define_train_set.py`, `phase_b_define_val_clusters.py`,
`phase_g_build_val_jobs.py`, `phase_h_search_templates.py`, `select_cache_structures.py` and
`cluster_composition.py`. The MSA phases (C–F) and the fold driver (`phase_i_fold_validation.sh`)
were spot-checked, not read in full.

## 1. CONFIRMED AND LIVE — `train_clusters.csv` is stale; validation leaked into training

**Where.** `phases/phase_b_define_val_clusters.py:129` (`train_minus_val`), and the artefact
`train_val_splits/train_clusters.csv`.

`train_minus_val` hardcodes the validation list as `train_val_splits/val_clusters.csv` — the ORIGINAL 50
phase-B clusters. The 2026-10-13 redesign moved validation to 40 clusters chosen under new rules
(`scripts/propose_val_split.py`), writing `train_val_splits/val_split_proposal_clusters.csv`. Nothing
regenerated `train_clusters.csv`, and nothing compares the two files.

**22 of the 40 live validation clusters are listed in `train_clusters.csv` as training.**

The function's own docstring says it is "THE ONLY PLACE THE TRAIN/VAL SPLIT IS ENFORCED". That was
true of the old split and is now false, which is what made it invisible.

**Blast radius.** The FT3 cache selection built from that file held 44 structures in validation
clusters, 28 of them structures actually folded into the validation set:

    7r58 7sqw 7su0 7tzh 7zmk 7zra 8apy 8gq1 8og0 8piz 8pjp 8tbq 8v8f 8xqj
    8z2v 8z3a 8z74 9bx7 9c7x 9cfd 9cn2 9fgy 9ima 9lme 9nr6 9rye 9ryf 9y7n

Nothing was folded or trained against it; the leak existed only in a committed CSV.

**Status.** Fixed in `scripts/select_cache_structures.py` (commit `8208efea`): it subtracts the live
validation split first, prints how many clusters that removed, and asserts none survive. Selection
went 668 rows / 666 structures / 224 clusters → 624 / 622 / 202.

**NOT fixed.** `train_val_splits/train_clusters.csv` itself is still stale on disk, and `train_minus_val`
still points at the old file. Any future consumer inherits the bug.

## 4. FAIL-OPEN in the CDR-H3 leakage check

**Where.** `phases/phase_a_define_train_set.py:408`.

```python
try:
    _s, numbered, details, _h = m.run_anarci(...)
except Exception:        # noqa: BLE001
    continue
```

A sequence ANARCI cannot number is skipped, so it contributes no CDR-H3, so it can never trigger the
≥95% CDR-H3 exclusion. There is no assertion on how many of the input chains produced a CDR-H3.

This matters because ANARCI is known-fragile in this environment: it parses `hmmscan` text with
Biopython's `Hmmer3TextParser`, which cannot read HMMER 3.4 (the system version), and on that
mismatch `run_anarci` returns no domains rather than raising. The project works around it by pinning
HMMER 3.1b2 and re-pressing the HMMs.

**The observable consequence:** the CDR-H3 check reportedly excluded **0 clusters**. That is equally
consistent with "no CDR-H3 leakage exists" and with "the check silently numbered nothing". Those two
cannot be told apart from the recorded output.

**Suggested fix:** count chains in versus CDR-H3s out, and fail if the ratio falls below a threshold.
A leakage check that finds nothing should have to prove it looked.

## 5. FAIL-OPEN in the antigen homology check

**Where.** `phases/phase_a_define_train_set.py:445`.

```python
try:
    aln = al.align(q.upper(), t.upper())[0]
except Exception:        # noqa: BLE001
    return 0.0, 0.0
```

An alignment failure returns identity 0.0 — indistinguishable from "these sequences are unrelated".
Same class as finding 4: in a leakage detector, the error value must not be the safe value. Biopython
raises on, among others, sequences containing characters outside the alphabet, which is exactly the
case a curated set would hit on an unusual residue code.

**Suggested fix:** return `None` and make the caller treat it as "could not determine", counted and
reported, rather than as "not homologous".

## 6. LATENT — phase H's shared-directory cutoff is computed over the subset it is given

**Where.** `phases/phase_h_search_templates.py:161-172`.

Template cutoffs are per structure, `min(own_release_date - days, 2021-09-30)`. MSA/template
directories are keyed by SEQUENCE, so one directory can serve several structures, and the code takes
the strictest cutoff across them — but only across the jobs in the current invocation:

```python
if d not in per_dir or cut < per_dir[d]:
    per_dir[d] = cut
```

Run phase H on a subset and a shared directory gets the minimum over that subset, which can be looser
than the true minimum. This has already happened once: a shared directory was rewritten from a
pre-cutoff structure's strict date up to the 2021-09-30 cap.

**Why it is low risk for the FT3 training run as scoped:** every selected structure is post-cutoff, so
`own > 2021-09-30` and the global cap binds for all of them — all cuts are equal, so the minimum
cannot be wrong. **It becomes live** the moment pre-cutoff structures enter, which is exactly what the
proposed control arm does.

**Suggested fix:** compute `per_dir` over every job that references the directory, not over the jobs
passed in; or refuse to lower an existing recorded cutoff.
